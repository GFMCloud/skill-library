## Classification

### 1. The bash-guard rule set as a delivery mechanism (14 rules, `hooks/bash-guard.py`)

Splitting this bundle by rule, against the ratified destructive-command hook in `docs/runbooks/2026-09-03-hooks-and-permissions.md` Step 1:

- **`r_git_safety`'s force-push clause — REDUNDANT.** The runbook's hook already blocks this: *"positive control (`git push --force origin main`) denied"* (`hooks-and-permissions.md:31`). Candidate: `bash-guard.py:210-213` — `git push --force` without `--force-with-lease` → `BLOCK`. Same coverage, same verdict.
- **`r_git_safety`'s `git reset --hard` clause — weaker than what's installed, a philosophy conflict (see below), not a substitute.**
- **`r_catastrophic` (fork bomb, `dd` to raw device, `curl|wget` piped to shell, `mkfs` on a device, `chmod 777 /`) — COMPLEMENT.** None of these patterns appear in the runbook's derived list (`rm -rf` outside scratchpad, force-push, reset --hard, branch -D, `aws s3 rm --recursive`, Route 53 delete, `terraform destroy`, `DROP TABLE` — `hooks-and-permissions.md:21-23`). Gap: nothing on this machine currently blocks a downloaded-script-piped-into-a-shell or a fork bomb at the Bash-hook layer.
- **`r_pipe_masks_exit_code`, `r_stderr_discarded`, `r_measurement_silenced`, `r_delete_before_verify`, `r_time_based_delete`, `r_arbitrary_row_from_listing`, `r_guessed_unit_candidates`, `r_empty_grep_as_absence` — COMPLEMENT, and a strong one.** These mechanize the exact silent-failure shapes that CLAUDE.md's "Evidence over assertion" section describes as prose incidents (*"A tool's output is proof of what you checked, not of what exists"* — `CLAUDE.md:19-20`) but has never mechanized at the command layer. Nothing installed currently intercepts a Bash command for "pipe into tail masks the real exit code" or "counting grep read as absence of evidence." This is real, unclaimed ground.
- **`r_secret_exposure` (Bash-level: literal secret in an export, `sshpass -p`, credential piped to network, credential file printed to stdout) — COMPLEMENT.** The installed set has no PreToolUse Bash-layer secret detector; the CLAUDE.md secrets doctrine (*"Secrets live in `.env` or a keychain... secret-scan before every commit"* — `CLAUDE.md:57-59`) is a pre-commit-time check, not a pre-execution one. This closes a different, earlier gap.
- **`r_config_guard` — COMPLEMENT, broader than what exists.** It WARNs on any edit to `.claude/settings*`, `.claude/hooks/`, or the guard scripts themselves. The installed mechanism that touches this territory is Claude Code's own auto-mode classifier, which per CLAUDE.md only blocks *"edits whose content grants standing autonomy"* (`CLAUDE.md:207-209`) — narrower, since it doesn't fire on a legitimate restriction being added quietly. This rule adds visibility the classifier does not provide.
- **`r_package_install`, `r_cuda_without_gpus` — COMPLEMENT**, narrow but real (no installed equivalent for either).

**What would have to change before any of it is trusted**: every one of these rules needs to go through `prove-hooks.sh`'s positive/negative-control proof against the actual wired `settings.json` command, not just the candidate's own in-process rule-function tests — the ratified standard on this machine is that "a gate or validator is trusted only after being proven by deliberate failure" (`CLAUDE.md:32-33`), and that proof has to run against the live hook invocation, the exact distinction row 1 of the hstack decisions makes.

## Routing collisions

No name collision — there is no installed skill named `oops-i-did-it-again`, so nothing misroutes on name lookup.

There **is** a real description-level collision between the candidate skill and the installed **`retro`** skill, and it is the dangerous kind because both plausibly fire on the same trigger with **different bodies and different governance models**:

- Candidate: *"Run IMMEDIATELY after any mistake, wrong claim, false pass, or correction... Also use when a 'green' result looks too good"* (`SKILL.md` frontmatter) — triggers **mid-session, on the mistake itself**, and its Step 3 directly instructs writing to `hooks/bash-guard.py` and appending to `~/.claude/oops-ledger.md` with no approval gate.
- Incumbent: *"Write a short, gated, transcript-grounded retro for the current session... route each lesson to where it actually belongs (memory, project CLAUDE.md, an ADR, a hook, or nowhere)... Exits silently, producing no file, when none of those happened"* (`inventory.md` row for `retro`) — triggers **at session-end**, and explicitly **proposes** a destination rather than writing to it: *"it proposes destinations and the session (or user) acts on the proposal"*.

For a typical prompt like "oh, that was wrong" mid-session, the candidate's immediate-trigger description would win over `retro`'s session-end framing — but if both were installed, a single incident could get logged twice (once to `~/.claude/oops-ledger.md` by the candidate, once proposed into `.claude/retros/` by `retro` at session end), with no reconciliation between the two logs. Worse, they'd disagree on write authority for the *same kind of output*: the candidate skill's own text authorizes writing hook code directly; `retro`'s text explicitly forbids that ("never touches CLAUDE.md, memory, or a decisions/ ADR directly"). Installing both without resolving which owns "a mistake just happened" would be exactly the "identical name, different body" failure mode the task calls the worst case — here it's not an identical name, but it is an identical *trigger surface* with contradictory bodies, which is just as dangerous because nothing about the file listing would look wrong.

## Philosophy conflicts

**1. How broadly to mechanize a style rule.** The installed, ratified decision narrowed em-dash enforcement to `Artifact` publish only: *"Scope stays `Artifact` publish. Widening to Write or Edit is a separate ruling"* (`hooks-and-permissions.md:41`). The candidate's `style-guard.py` mechanizes the same underlying CLAUDE.md rule (*"No em dashes, ever, anywhere"* — `CLAUDE.md:172`) at every Stop event, i.e. every assistant turn — a strictly wider scope than the one this machine deliberately chose. These are not different emphases; one says "here, and only here" and the other says "everywhere, by default."

**2. How severely to treat `git reset --hard`.** The installed destructive-command hook **BLOCKs** it outright (`hooks-and-permissions.md:21-23,31`: it's in the same pattern list as force-push and repo deletion, no WARN tier described). The candidate's `r_git_safety` **WARNs** on it: *"this git command discards uncommitted work irreversibly. Confirm there is nothing unsaved first"* (`bash-guard.py:214-216`) — proceeds by default, on the strength of the candidate's own house doctrine that *"BLOCK is only for traps that are never legitimate"* (`README.md:178`). Both sides have a considered position; they contradict on the same command.

**3. Who owns the decision to add a new standing restriction.** CLAUDE.md's "Boundaries are declared and enforced" section holds that boundaries are *"Name[d]... before the work starts"* and that irreversible or intent-changing actions are standing escalation triggers (`CLAUDE.md:85-95`). The candidate's `SKILL.md` Step 3 instructs, as an unconditional step of ordinary skill execution, writing a new BLOCK/WARN function directly into `hooks/bash-guard.py` the moment a mistake is classified as mechanisable — no confirmation step is described. On this machine, the equivalent action (the destructive-command hook) went through a named, one-session, gated runbook with recorded proofs (`hooks-and-permissions.md`) rather than being auto-applied by a skill mid-task.
