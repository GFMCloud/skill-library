# voice-and-editing

Part of [skill-library](../../README.md). If the words skill, pack or agent are new to you, that page explains them first.

## What problem this solves

Two different problems sit in this pack. The first is writing: text that Claude Code produces reads like a chatbot, with the same contrasts, the same closing lines and the same stock words in every paragraph. The second is procedure: jobs you do by hand every few months, such as turning a folder into a repository, handing a project to someone else without your personal files going with it, or reviewing something you already built. Done from memory, they go wrong in the same places each time.

This pack is one person's answers to both. It is the author's own writing voice and the tools he built around his own computer, his own accounts and his own projects. It is published so you can read it and change it, not as a set of defaults for you. Where a skill names a folder, a naming rule, an account or a way of speaking, that is his, and the pages here say so rather than assuming it is yours.

- **Work for anyone as they are:** `humanizer`, `fable-project-review`, `scrollback`, `repo-handoff`, `schedule-harness`, `skill-discovery`, `adhd`. `x-read` also works for anyone, on an Apple computer, after you do its one-time setup with your own X account.
- **Change them before you use them:** `graham-voice` is one named person's voice, down to his name and sign-offs, so it is a model to rewrite rather than a skill to run. `capability-index` lists the author's own unloaded projects, so it is empty until you fill in your own. `folder-to-repo` names repositories by the author's own rule. `source-intake` and `toolkit-review` expect a copy of this repository at `~/skill-library` that you own and can commit to.

## When would I use this?

- Something you wrote with Claude Code reads like a chatbot and you want it to sound like a person again.
- A folder on your computer has grown into a real project and you want it on GitHub, privately, without a password or key going up with it.
- A friend or colleague wants to run a project you built around your own data, and none of that data can travel with it.
- You finished building something and want a hard review of it, with a plan another session can carry out.
- You want a web page or a dashboard that looks like a terminal window rather than a brochure.
- You want to see how somebody else set up a personal writing voice and a set of tools, so you can build your own.

Two limits. First, the secret scan in `folder-to-repo` is weaker than its name sounds, in two ways: it skips any line containing a word like "example", "test_key", "dummy" or "changeme", so a real key sitting on such a line is passed over silently, and when it does find something it prints up to sixty characters of the match, which means part of a real key appears in your session transcript. A clean result is a good sign, not a guarantee. Second, neither `folder-to-repo` nor `repo-handoff` checks which GitHub account is signed in before it creates a repository, so on a computer signed in to two accounts the new repository can land under the wrong one. Check it yourself first.

## How the skills work together

They are independent. Each covers a different moment:

1. **While writing:** `graham-voice` drafts in one person's voice. `humanizer` takes the chatbot out of text that already exists.
2. **While reading a reply:** `adhd` reshapes how Claude Code answers you for the rest of the session.
3. **When a folder becomes a project:** `folder-to-repo` puts it on GitHub privately, after a secret scan.
4. **When somebody else wants your project:** `repo-handoff` cuts a copy with your personal material removed and proven gone.
5. **When something is built and you want it judged:** `fable-project-review` reviews it and writes a plan another session carries out.
6. **When you are building a page:** `scrollback` gives it a fixed terminal-style look.
7. **When you are deciding what to keep:** `source-intake` judges one incoming repository or article. `toolkit-review` judges the skills you already have. `skill-discovery` reads your past conversations for jobs you keep redoing.
8. **When a long project should run unattended:** `schedule-harness` writes the instruction file for a scheduled run, which you then register yourself.
9. **When you want to read a post on X in full:** `x-read` fetches it.

## Install

Inside a running Claude Code session:

```
/plugin marketplace add GFMCloud/skill-library
/plugin install voice-and-editing@skill-library
```

The first line is only needed once, however many packs you install.

Some skills need other free software. `folder-to-repo` needs Python and git, and either a connected GitHub tool or the `gh` command line tool signed in. `repo-handoff` needs git, `gh` signed in, and `gitleaks`, a secret scanner; it stops before creating anything if `gitleaks` is missing. `schedule-harness` and `scrollback` need Python. `source-intake` needs git, `gh` signed in, the `anydoc` or `markitdown` converter, and a working `claude` command that can run without a person watching. `toolkit-review` needs `jq`, Python, `bash`, git and `gh`, and Docker for its largest size only. `x-read` needs an Apple computer, Node version 22 or newer, and a signed-in X account whose two cookie values you store once by running its setup script yourself. The rest need nothing extra.
