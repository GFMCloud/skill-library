### For each item

**item-92c76be2**
- **Trigger:** Skill, loads on demand — its description says to use it "when presenting verification results, acceptance checks, or any claim that work is done." Not always on.
- **What it makes the agent do:** Take claims plus the check/output already produced for each and write one block per claim with four labeled fields (CLAIM, CHECK, OUTPUT, VERDICT), where OUTPUT is the actual returned text quoted rather than paraphrased and VERDICT names the failure mode it rules out rather than just a pass/fail word. It must close every report with a "NOT VERIFIED" section listing what was not checked and why, present even when nothing was skipped, and must never write it as "none" implicitly by omitting it. It requires reporting the error count rather than a tool's reassuring wording, and attaching an identifier (a count, hash, timestamp, or path) to each verified/failed claim. If a check could not be run, the instruction is to record the claim as unverified with the reason rather than reasoning about why it probably works.
- **Enforcement:** An executable script, run as `scripts/check-report.py <report>`, parses the report for the four fields per block, checks the verdict token is one of three allowed values, requires non-empty OUTPUT on verified/failed verdicts, applies a heuristic identifier check, and requires the not-verified section to exist with an entry or the word "none." It exits 1 and prints one line per failure otherwise, exits 0 with a block count on success. The file documents its own limits: the identifier check is a heuristic that a decorative number would satisfy, and it "cannot tell whether a CHECK was run, only that its OUTPUT is empty" — so it fails closed on missing fields but cannot catch a fabricated OUTPUT paired with a check that never ran. Nothing in the files shows this script being invoked automatically; it appears to be run manually or by an agent choosing to run it.
- **Dependencies:** python3 to run the checker script. No other CLI or service.
- **State it writes:** None. The checker script only prints to stdout and sets an exit code; the fixtures are static sample reports, not generated output.
- **Fit with the bar:** Plan then stop before consequential work — not addressed; the skill operates entirely after checks have already been run. Executed evidence before "done" — supported indirectly: it enforces the shape evidence must take (quoted output, an identifier) but does not itself execute anything, and its own eval prompt tells the agent "Do not re-run anything; format what is here." Say what was and was not checked — directly supported: the not-verified list is mandatory ("An omitted not-verified list reads as 'everything was checked'") and one of its two evals exists specifically to confirm the list survives when nothing was skipped.
- **What it does not cover:** Whether a CHECK actually ran (stated weakness); it only formats and shape-checks, leaving execution to the companion evidence-standard skill; the identifier heuristic can be satisfied by an unrelated number; no coverage of planning or pre-work stop conditions.

**item-7aed43c3**
- **Trigger:** Skill, loads on demand — described for use "before declaring any artifact complete, and whenever a tool reports its own success." Not always on.
- **What it makes the agent do:** Actually run the check ("Run the thing... Grep, lint, type-check, and self-review do not count as verification where the failure mode can hide from them"), state what was run, against what input, and what came back, and verify at the level where the failure would actually show up. For multi-step work it requires declaring the check before the step runs (`step -> verify: check`). It explicitly requires independently inspecting what a tool claims to have produced rather than trusting a tool's own success message, citing three prior cases where a success message was wrong. For code artifacts it directs running the ordered sequence (build, types, lint, tests, secrets, diff) through its check-running script rather than recalling results informally. When evidence genuinely cannot be produced, it requires saying so in those words, logging it as not verified, and handing over the exact command for a human — only after confirming the agent itself truly cannot run it.
- **Enforcement:** An executable script, `scripts/run-checks.sh <log-dir> [checks-file]`, runs each phase via `bash -c`, writes each phase's stdout/stderr and exit code to its own file, and marks a phase "ran" only if an exit code was actually captured, "not-run" if the phase's tool is absent, and "skipped" if it comes after a stop-phase (build or tests) failure. It exits 1 if any phase failed, 3 if any could not run, 0 otherwise, and reads its summary back from the per-phase files so a phase can't be reported as passed without a captured exit code — including a tamper case where a summary line falsely claims "ran" but is overridden to "not-run" because the exit file is missing. Its own correctness is checked by a fixture-proof script exercising a green, a red (stop-on-test-failure), and an absent-tool sequence, each asserting the expected exit code and status text.
- **Dependencies:** bash, python3, node, npm, gh.
- **State it writes:** Under the log directory passed as an argument: one `<n>-<phase>.out` file per phase (plus a matching `.exit` file recording the exit code), and a `summary.tsv` listing phase, command, status, exit code, and output path. The fixture-proof run uses a temp directory that is removed on exit.
- **Fit with the bar:** Plan then stop before consequential work — partially touched: it requires naming the check for each step before the step runs, but this is about declaring a verification method in advance, not pausing for approval before a risky action, so it does not directly address stopping before consequential work. Executed evidence before "done" — strongly supported and central to the item: "Executed evidence is attached to every claim of completion," and a self-reported success is explicitly not accepted as evidence on its own. Say what was and was not checked — supported: it requires stating all three of what ran, against what input, and what came back, and to log genuinely-unrunnable checks as not verified with a reason rather than substituting reasoning.
- **What it does not cover:** It does not itself produce the formatted write-up (that is a separate item's job); its automatic check-sequence derivation only recognizes JS/TS and Python project layouts, so other stacks need a supplied checks-file; it flags its own gap that a green pre-filter sequence is not evidence the changed behavior itself was exercised ("A green sequence with no run of the new behavior is not evidence for it"); nothing in the files forces the agent to invoke the skill or its script rather than skip it.
