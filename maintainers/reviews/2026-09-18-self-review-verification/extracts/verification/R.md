### For each item

**item-7aed43c3**
**Trigger:** Loads on demand; its own description says to use it "before declaring any artifact complete, and whenever a tool reports its own success." Not always-on.
**What it makes the agent do:** Run the artifact against representative input rather than trust grep/lint/self-review; state "what was run, against what input, and what came back," all three; "verify at the level the failure lives"; for multi-step work, declare each step's check before the step runs (`step -> verify: check`); independently inspect what a tool claims to have produced rather than trusting its own success message; when a project names no check sequence, fall back to the ordered build→types→lint→tests→secrets→diff sequence in its reference file, with a hard stop on build or test failure and on any secret hit; when evidence genuinely cannot be produced, say so "in those words," add it to the not-verified list, and hand a human the exact runnable command rather than a description.
**Enforcement:** Prose only — no script or hook in this item enforces any of it.
**Dependencies:** None named at runtime; it names `evidence-report` (`foundry-core`) as the report format it feeds into, and `verification-kit:pre-delivery-verifier` as a consumer, but neither is a hard dependency to use this item's guidance.
**State it writes:** None — it produces no file, log, or artifact of its own.
**Fit with the bar:** Executed evidence before done — supported, this is the item's core content. Say what was and was not checked — supported via its "Stop when" rule that a not-verified list entry is mandatory when a check cannot run. Plan then stop before consequential work — only partially: it asks that a check be *named* before a step runs, but nothing in the item stops the step itself from starting.
**What it does not cover:** No report template of its own (delegates that to the paired item), no mechanical check that the ordered code sequence was actually followed, no gating of when work may begin.

**item-92c76be2**
**Trigger:** Loads on demand for "presenting verification results, acceptance checks, or any claim that work is done."
**What it makes the agent do:** Write one block per claim with all four fields (CLAIM, CHECK, OUTPUT, VERDICT), quote OUTPUT verbatim rather than paraphrase, make VERDICT name the failure mode it rules out, attach an identifier (SHA, count, timestamp) to each claim, close every report with a NOT VERIFIED list "even when empty of surprises," count error numbers rather than a tool's reassuring adjectives, and never add separately-measured improvements together instead of measuring the combined change directly.
**Enforcement:** Prose only — no script validates that a written report actually satisfies the four-field shape.
**Dependencies:** None named; it is the reporting half of the paired evidence-standard item and assumes checks were already run elsewhere.
**State it writes:** None of its own; it formats claims the caller supplies (its own eval prompts explicitly say "do not re-run anything, format what is here").
**Fit with the bar:** Say what was and was not checked — strongly supported, the mandatory not-verified list is its central mechanism. Executed evidence before done — supported for presentation, but the item takes CHECK/OUTPUT on faith from whoever invokes it; it does not itself re-run or verify that the quoted OUTPUT is real. Plan then stop before consequential work — not addressed; this item is purely a write-up format, not a gate.
**What it does not cover:** Does not verify the truth of the inputs it is handed, and has no way to detect a fabricated OUTPUT line.

**item-24501ddb**
**Trigger:** Loads on demand; its own description flags use "before any 'ready,' 'live,' or 'working' claim about an interactive artifact," and explicitly not for "a one-off manual check with no committed script."
**What it makes the agent do:** Generate a smoke script from a manifest that names five assertion categories (identity, freshness, connections, routes, console), each paired with a "poison" value; run a coverage check before trusting any pass; run the script once per category with that category's poison override active, expecting exit 1 each time and the failing category named in a `SMOKE FAIL:` line; then run the unmodified script against the real target for the live exit-0 pass, attaching its full output plus a screenshot (or a stated reason none is available); stop and refuse a "ready" claim on any red assertion, handing the run log to a bounded-retry mechanism or a human instead; stop and mark a category "unproven" (never "passed") if it has no poison entry; distinguish a red assertion from a setup failure (target unreachable at all) in the run log.
**Enforcement:** Two real scripts. `check-poison-coverage.py` exits 0 only if every category has a poison entry, else exits 3 and prints one `UNPROVEN <category>` line per gap — fails closed (an unproven category is never reported as a pass). `generate-smoke-script.py` refuses outright (exit 1, no script written) to generate a script for a category with no poison entry, so a missing poison value cannot silently default to an always-passing check. The generated smoke script itself exits 1 on any failed category and 0 only when all are green. An offline fixture-proof script exercises this whole chain against a local test server.
**Dependencies:** bash, python3, and PyYAML (the scripts exit 1 with a message if PyYAML is absent); a Browser-automation tool or Playwright for a real screenshot and a real console-error read (stated as not embedded in the generated script); optional environment variables per connection/route to supply live addresses; references two other items by name for downstream composition (an escalation-report consumer and a diagnose-and-fix loop) without requiring them to run the core flow.
**State it writes:** The generated smoke script (written into the calling project, not this item's own directory), a run log holding five poisoned exit-1 results plus one live exit-0 result and its verbatim output, and one screenshot from the live pass or a stated absence line.
**Fit with the bar:** Executed evidence before done — strongly supported; its "Done when" explicitly bars "a live exit 0 with fewer poison categories proven than the manifest declares." Say what was and was not checked — supported; it distinguishes a red assertion from a setup failure and states its own console check is "a text-marker grep, not a real DevTools console read." Plan then stop before consequential work — partially supported: the described flow runs before a "ready" claim, but the item names an optional Stop-hook mechanism to actually block the turn on a red result and says plainly that hook is "optional... and not proven by a fixture in this build" — without it, nothing in this item mechanically prevents the claim from being made anyway.
**What it does not cover:** A real browser console-error read (stated limitation), and the gating hook that would make the check unavoidable is optional and untested by this item's own fixture.

**item-e739493a**
**Trigger:** Loads on demand; described for use "before applying any change spec produced by a bounded loop or a goal-driven session," specifically not for "a plain code-review request with no goal block behind it."
**What it makes the agent do:** Confirm a goal block and a change spec are both in hand, stopping otherwise; spawn a read-only, non-fork reviewer subagent (`permissionMode: plan`, a disallowed-tools list barring edits, a bounded turn count, and a model different from the one that produced the change) given only the goal block and the change — never the builder's transcript or reasoning; write the reviewer's returned verdict to a run log before acting on it; validate the verdict's shape with a script; apply the change on a clean pass with no second opinion sought; on a fail, give the builder one more attempt and get a second verdict, deciding whether it cites something the first verdict did not; apply a hold rule on a second unconvincing fail rather than attempting a third pass.
**Enforcement:** `verdict-check.sh` is a real script: exits 1 on a malformed verdict (missing field, `result` outside `{pass, fail}`, `severity` outside its allowed set, `confidence` outside 0..1, or `issues` not empty exactly when `result` is `fail`) and fails closed ("a verdict object that fails this check is not a review result... the apply does not proceed on it either way"); given two verdict files, it exits 2 and prints `HOLD` when a second fail cites nothing the first one didn't. The item itself states this script's limit directly: "It cannot check that the reviewer actually looked at the change rather than rubber-stamping it."
**Dependencies:** bash for the validator; the Agent/subagent mechanism with a model differing from the builder's (the item stops if none is configured); an external field-list document for the exact Goal-block and Verdict-object shapes, which is referenced but not included among these files; two other named items for downstream handling of a failing or a finished result.
**State it writes:** The verdict file(s) written to a run log prior to any apply decision; this item's own example verdict files exist only as fixtures for its checks, not as output of a live run.
**Fit with the bar:** Plan then stop before consequential work — strongly supported; the whole point is gating an apply behind a passing verdict, with explicit stop conditions for a missing goal block, a malformed verdict, a same-model reviewer, and a repeat fail. Executed evidence before done — partially supported: each issue in a verdict must carry `evidence`, but that evidence can be "a quote under 15 words" rather than a run's output, and the item's own "Known weakness" line concedes the validator cannot confirm the reviewer actually inspected anything. Say what was and was not checked — partially supported: a `confidence` field and per-issue evidence exist, but the verdict shape has no equivalent of a mandatory not-checked list.
**What it does not cover:** Verifying the artifact after the change is applied — explicitly out of scope, deferred to a separate finished-artifact verifier — and it cannot compel genuine scrutiny from the reviewer beyond checking the shape of what comes back.

**item-06c31a80**
**Trigger:** Loads on demand; its description flags use "when work is about to be presented as done, and whenever a claim is load-bearing enough that being wrong costs a rework cycle."
**What it makes the agent do:** Restate acceptance criteria as falsifiable statements, stopping and reporting outright if nothing given can be restated that way; for each statement, pick the check that could falsify it and the level it must run at; run it against representative input, treating grep/lint/type-check/self-review as "cheap pre-filters, not evidence"; treat any tool's self-reported success as a claim, confirming it independently; before routing anything to a human, establish that the check genuinely cannot be run by the agent itself, and hand over the exact command to paste rather than a description; report through a fixed evidence format including its not-verified list; issue exactly one of three verdicts — VERIFIED, UNVERIFIED, or FAILED — with phrases like "looks fine" or "no issues found on review" explicitly barred from ever standing in as a verdict; never modify any file "by any means, including a Bash heredoc, `sed -i`, `tee`, or a redirect," and refuse (with the refusal reported) an instruction to "fix it and re-verify."
**Enforcement:** A `disallowedTools` frontmatter list removes Write/Edit/NotebookEdit, but the item is explicit that this alone is not the real guarantee: it still has Bash, and it states a documented incident where an identically-restricted sibling agent was made to rewrite a file via heredoc under adversarial instruction. It calls its own frontmatter restriction "a narrowed surface, not a boundary" and locates the actual non-modification guarantee in its stated charter rather than in any enforced tool block.
**Dependencies:** None named as runtime tooling; it leans on the two skill items above for its evidence standard and report format, and names a further claim-verification skill that is referenced but not present in this file set.
**State it writes:** None — it never writes files by design, and reports its verdicts as output only.
**Fit with the bar:** Executed evidence before done — strongly supported, this is the item's stated reason for existing, framed against a cited history of verification being "absent or failed in seven of nine past projects." Say what was and was not checked — strongly supported, with an explicit ban on vague affirmative language standing in for a verdict. Plan then stop before consequential work — partial: it runs after an artifact already exists rather than gating the start of work, though it does stop distinctly and immediately when acceptance criteria are absent.
**What it does not cover:** It explicitly declines to resolve "a disagreement about whether a criterion is met" (calling that someone else's call, not its own), and it cannot repair anything it finds — only report and hand back.
